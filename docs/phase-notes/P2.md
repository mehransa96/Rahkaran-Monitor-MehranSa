## Safety findings while building P2

- `M:Type.set_Property(…)` ban entries were silently ignored by the analyzer (P0 gap): property setters of
  `FileInfo`/`FileSystemInfo`, `Process` and `PerformanceCounter` were not actually banned. All are now `P:` entries;
  canaries prove they fire; a test forbids `M:…set_` entries. CIM/PDH bans are now canary-checked as well.
- New catalog test: every session/request view excludes RSM's own sessions; it caught P1's `sql.tempdb.contention`.
- `system_health` file pattern: the log path may lack a trailing separator; the query adds one, and the collector falls
  back to the ring buffer when files return nothing (CI's Linux container needed the fallback).

## Evidence — CI, real SQL Server 2022 container, least-privilege `rsm_monitor` (run 14, `be60bdf`)

- All 7 integration tests passed; **read-only proof: fingerprint diff before/after is empty**.
- **Blocking demo** (two app sessions, admin connection, rolled back): `sql.blocking.chains = 1`,
  `head_session = 70`, `head_idle = True`, `max_wait_s = 4.04`, summary "session 70 (… Rahkaran demo app (CI),
  sleeping, transaction open 4 s) blocks 1: UPDATE dbo.RsmDemoAccounts …"; the blocked session, its LCK_M_* wait, the
  request and the open transaction are all asserted.
- **Deadlock demo**: read from `system_health` (ring buffer in the container) and parsed: "victim 71 (UPDATE
  dbo.RsmDemoAccounts … WHERE Id = 1;) vs 70 on Rahkaran.dbo.RsmDemoAccounts (X)"; victim, both statements, object,
  lock modes, application and database asserted; a `xml_deadlock_report` event is raised.
- **Soak (75 s, live view, all SQL live collectors)**: 12 collector runs/min, 0.47 s of query time per minute
  (upper bound of RSM's server CPU: ≤ 0.8 % of one core), RSM SQL CPU from `cap.self_overhead` 0.000 % (lower bound —
  whole-millisecond accounting), round trip 0.6 ms, nothing backed off, every collector Ok, client working set 176 MB.
  Live findings on the container: SQL-MEM-007 (PLE fallback), SQL-PLC-001.
- **Full diagnosis** now runs 15 collectors (all Ok except `sql.errorlog` Partial: `xp_readerrorlog` denied, as
  designed). The live rules that need several samples (`…_min3`, `…_min5`, `…_max60`) are *undecided* in a one-shot
  diagnosis and decided in the live view; Windows rules are undecided on the Linux runner (no Windows transport).

## Not verifiable here — needs a Windows lab

- **1-hour stability on a loaded lab server** and the memory ceiling over that hour: CI runs 75 s on an idle
  container. Suggested check: connect the live view to a Rahkaran test server under load for 60 min and read the
  overhead line (RSM SQL CPU, query time, working set) at the end.
- Windows collectors against real Windows (PDH locally, CIM remotely, registry): unit-tested with fixture rows; the
  Windows CI job builds and runs the unit tests but has no SQL Server or remote host.
- The dashboard has not been looked at on a screen (no Windows desktop here): layout, RTL and chart readability need a
  visual pass.
